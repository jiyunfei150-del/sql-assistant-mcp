SQL 助手：怎么用 MCP 接数据平台

经验总结 · 2026-11-17 · 基于 SQL 助手 2026-10-08 上线以来的实现与排障

一句话：SQL 助手不连库、不存元数据，所有能力都通过 MCP 向 db-query 平台要。我们自己只写了一层「平台会话」，把平台公布的工具筛选、去掉身份参数后交给模型，调用时再由服务端补上身份。剩下的工作都是让这条链路在真实平台上稳定可用。

接法：四步走完一轮

1建连官方 mcp SDK 的 SSE 客户端；account_hash_id 拼进地址圈定身份
2开轮取上下文get_key_info 拿账号、项目、库类型；list_tools 拿工具声明，两者并发
3改造成模型工具白名单筛选、剔除身份参数，再加上自己合成的两个工具
4循环调用模型调工具 → 服务端注入身份转发 → 结果回填，直到交卷过守门

代码位置：通道 scripts/dbquery/channel.py，身份链 scripts/dbquery/identity.py，平台会话 scripts/agents/apps/sql_assistant/platform.py，工具循环 …/sql_assistant/agent.py。

做对了的六件事

1. 工具声明直接用平台的

参数 Schema 取自 list_tools 的 inputSchema，不在我们这边另写一份。

公布的就是校验的；平台加参数、改说明，我们不用改代码。

2. 身份由服务端注入，模型看不见

account_hash_id、key_index、question、model_name 从声明里删掉，调用时再补上。

模型无法冒用身份，权限永远等于提问人本人在平台上的权限，不用自建权限体系。

3. 白名单开放，执行通道不给模型

只开放搜表、读结构、规范、EXPLAIN 校验；submit_sql_query 只留给服务端内部拼 SHOW CREATE TABLE。

助手的边界由工具清单决定，不靠提示词约束。

4. 按账号能力动态挂工具

数仓资产、指标、知识三项只在项目开通洞察时挂；一个账号挂多个项目时让模型选，但只放行名下的项目。

模型看到的工具和真实可用的一致，少走冤枉路。

5. 在 MCP 之上合成自己的工具

show_create_table：平台没登记字段时读建表语句补结构。submit_answer：把「交付」也做成工具调用。

交卷有了结构化入口，守门（只读、表已读、字段存在、EXPLAIN 通过）才有抓手。

6. 平台通道做成公共层

scripts/dbquery/ 同时服务 SQL 助手和智能问数的 user_query 工具。

建连、证书、重试、错误拆包修一次，两边同时受益。

可以带走的经验

  1. MCP 服务端就是能力边界。接入方要做的是「挑、藏、补」：挑出该开放的工具，藏起身份和危险通道，补上业务需要的合成工具。
  2. 身份永远不经过模型。声明里删掉、调用时注入，这是用 MCP 做多用户服务最省心的权限方案。
  3. 让交付也走工具调用。有了 submit_answer，程序才能在交付前检查，而不是在模型说完后补救。
  4. MCP 调用失败要分级处理。建连失败重试；单个工具失败回给模型；只有平台整体不可用才停下这一轮。
  5. 平台的「通过」不等于正确。平台校验是必要条件，事实检查要自己补。
  6. 防打转的逻辑写在 MCP 调用层。重复调用拦截、步数和时间预算，都在工具循环里统一处理。
